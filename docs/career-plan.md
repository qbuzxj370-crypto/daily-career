# career-fit (가칭) — 설계 정본

> 이 문서는 **무엇을 왜 만드는가**의 정본이다.
> 작업 규칙은 `CLAUDE.md`, 진행 기록은 `docs/ref.md`.
>
> **이 파일은 MinjeKim의 `career-plan.md`를 대체한다.** 원본은 인프라/운영 트랙 구직자가
> 관제 전담 공고를 걸러내는 도구였다. 이 프로젝트는 **시장 요건 통계를 쌓고, 그 통계에
> 내 스펙을 대조해 지원할 곳과 준비할 것의 우선순위를 내는** 도구다. 파이프라인 형태는
> 물려받되 판정의 목적이 다르다. 원본 문서는 지우지 말고 `docs/upstream/`으로 옮긴다.

---

## 1. 한 줄 정의

**매일 워크넷 공고를 전량 수집해 요건 통계를 영구 누적하고, 그 통계에 내 스펙을 대조해
`지원할 수 있는 곳`과 `준비할 것의 우선순위`를 낸다.**

---

## 2. 3층 구조 — ②가 ③의 전제다

```
① 수집층   공고 목록 + 상세 본문. 원문 그대로, append-only, 영구 보관
                    ↓
② 통계층   요건 분포 — 전체 공고 기준. 필수/우대 · 요구 깊이 · 동반 출현 · 시계열
                    ↓
③ 개인층   통계 × 내 프로필 → 적합도 · 갭 · ROI 순위
```

**통계층을 건너뛰고 개인층만 만들면 갭에 순위를 매길 수 없다.** 이것이 이 설계의 핵심
주장이므로, 구현 순서에서 ②를 뒤로 미루면 프로젝트가 "공고 필터" 수준으로 주저앉는다.

### 왜 통계가 먼저인가

```
통계 없음:  "당신은 Docker가 없습니다"                     ← 사실. 그래서 뭐?
통계 있음:  "Docker는 백엔드 공고 38%가 요구합니다(필수 11%)"  ← 우선순위가 된다
둘 결합:    "Docker 하나 채우면 지원 가능 공고가 34% → 52%"   ← ★행동이 된다
```

> 📐 **위 숫자는 형식을 보이기 위한 예시이고 실측이 아니다.** 이 프로젝트에는 아직 수집된
> 데이터가 한 건도 없다. 기준선으로 쓰지 말 것.

마지막 줄이 이 도구의 최종 산출물이다. **`통계 × 프로필`이 없으면 절대 나오지 않는다.**
단일 공고만 보는 매칭으로는 "이거 하나 채우면 몇 %가 열리는가"를 계산할 수 없다.

### 통계의 4원칙

원본에 없는 부분이고, 여기서 품질이 갈린다.

1. **절대빈도가 아니라 필수/우대를 분리한다.** 공고의 기술 나열은 부풀려져 있다 —
   담당자가 "있으면 좋고"를 다 적는다. `Redis 언급 22%, 그중 필수 3%`에서 **두 숫자의
   간격**이 실제 정보다. 워크넷 상세가 `직무내용`과 `우대사항`을 별도 항목으로 주므로
   구조적으로 가능하다.
2. **요구 깊이를 함께 센다.** `Docker 38%`보다 `이 직군은 Docker를 운영 수준으로
   요구한다`가 쓸모 있다. 준비 방향이 달라진다.
3. **동반 출현 클러스터를 뽑는다.** `Docker` 단독보다 `Docker + K8s + CI/CD`가 같이
   나오는 공고 군집이 정보량이 크다. ROI도 **묶음 단위**로 계산해야 정확하다 — 인프라
   묶음을 채울 때 열리는 공고 수가 비선형적으로 뛴다.
4. **변화율은 데이터가 쌓인 뒤 붙는다.** 3개월치로 "Redis가 뜬다"를 말하면 공채 시즌
   효과와 구분되지 않는다. 9개월 이상이면 사이클 두 개가 들어와 추세와 계절성이 갈린다.
   **지금 할 일은 쌓기 시작하는 것이고, 지표는 나중에 공짜로 나온다.**

### 통계는 전량에서 뽑는다 — 선별 이후가 아니다

**프리스크린으로 버린 공고는 통계에서도 빠진다.** 그러면 시장 분포가 아니라 "내가 관심
있는 공고의 분포"가 되어 갭 우선순위가 무의미해진다.

다행히 요건 추출은 **사전 매칭이라 LLM 비용이 0이다.** 그래서:

- **상세 수집 + 요건 추출 + 통계 적재 → 전량**
- **LLM 설명 + 노션 발행 → 선별 후**

## 3. 판정의 두 축 — 절대 한 점수로 섞지 않는다

| 축 | 정본 | 묻는 것 | 출력 |
|---|---|---|---|
| **스펙 적합도** | `config/profile.py` | 내가 지원할 수 있나 | `FitScore` 1~5 + 갭 |
| **기피 조건** | `config/rules.py` | 가고 싶은 자리인가 | `Verdict` 적합/보통/위험 |

**독립이다.** 스펙이 완벽해도 기피 조건에 걸리면 위험이어야 한다. 합치면 "스펙이 완벽한
파견 공고"가 최상위로 올라온다. 노션에서도 두 열로 따로 보여주고, 정렬은
`Verdict ASC, FitScore DESC`.

### 3-1. 기피 조건 (`config/rules.py` 정본)

사용자가 확정한 3개다. 원본의 4대 기준은 **전부 교체된다.**

| 신호 | 등급 | 근거 |
|---|---|---|
| **SI·용역 파견 상주** | hard: `파견 근무`, `상주 근무`, `고객사 상주`, `아웃소싱`<br>soft: `고객사`, `SI`, `프로젝트 단위 계약` | 자사 서비스 경험이 쌓이지 않는다 |
| **야근·주말근무 상시** | hard: `주 6일`, `토요일 근무`, `야근 상시`, `초과근무 상시`<br>soft: `야근`, `탄력근무` | 상시가 문구로 확정될 때만 hard |
| **1인 개발 · 선임 없음** | **근로자수 1명이면 자동 확정**<br>hard: `1인 개발`, `혼자 개발`<br>soft: `대표 직속` | 사수 없이 배울 수 없다 |

**완화 규칙**: `SI·용역 파견 ← 자사 서비스`. SI 회사가 자사 솔루션도 개발하는 경우가
있어, `파견`이 soft로만 잡히고 `자사 서비스`·`자사 솔루션`이 함께 있으면 강제하지 않고
LLM 판단에 맡긴다. 원본이 `관제 ← 구축 조직 동거`로 겸업 공고를 살린 것과 같은 장치다.

⚠️ **과하게 막지 말 것.** 신입은 선택지가 적다. 원본 `ref.md`가 학력 필터에서 배운 것과
같은 함정이다 — 엄격한 기준이 지원 가능한 공고의 대다수를 지웠다(614 → 72). hard로 올릴
때마다 **실측으로 잔존 건수를 확인**할 것. `레거시·유지보수 전담`은 **의도적으로 뺐다**
— 유지보수는 신입 진입로로도 쓰이므로 통로를 스스로 줄일 이유가 없다.

### 3-2. 근로자수를 `rules.py`에 연결한다 — 결정됨

`worknet_detail.size_band()`는 처음에 의도적으로 연결하지 않았다(판정 기준 변경은 사용자
결정 사항). 사용자가 `1인 개발 · 선임 없음`을 확정했으므로 **이제 연결한다.**

```
size_band() == "소기업·1인"  →  RISK["1인 개발"] 강제
```

문구 매칭보다 정확하다 — `근로자수`는 숫자이고, `1인 전산` 같은 문구는 우연히 적힌 경우만
잡힌다. 연결 시 `tests/test_rules.py`에 테스트를 함께 추가한다.

## 4. 목표 직군

1목표는 백엔드. 조건에 따라 인접 직군으로도 가므로 **목록에서 지우지 않고 우선순위로만
조절한다**(slug 삭제는 노션 select 옵션과 기발행 페이지를 무효화한다).

| slug | 표시명 | 검색 키워드(초안) |
|---|---|---|
| `backend` | 백엔드 개발자 | 백엔드, 서버개발, Java 개발, 스프링, API 개발 |
| `web_dev` | 웹개발 (SI·자사) | 웹개발, 웹 프로그래머, JSP, 풀스택 |
| `public_it` | 공공·기관 전산직 | 전산직, 정보시스템 운영, 전산실 |
| `fullstack` | 풀스택 | 풀스택, 프론트엔드 백엔드 |

`public_it`을 넣은 이유: 정처산기·SQLD·리눅스마스터 2급이 **직접 가점되는 트랙**이라
보유 자격증이 처음으로 값을 하는 경로다.

**통계는 직군별로 따로 집계한다.** 백엔드와 공공 전산직의 요건 분포는 전혀 다르므로
합쳐 세면 둘 다 흐려진다.

## 5. 내 스펙 (`config/profile.py`)

```
LEVEL_BASIC(1) 문법·기본 · LEVEL_PRACTICE(2) 만들어 봤다 · LEVEL_WORK(3) 실무
```

> 🚩 **레벨 숫자는 전부 [추정]이다. 사용자가 확인하기 전까지 정본이 아니다.**
> 사용자가 말한 것은 기술 이름과 "클래스·상속·스프링부트까지", "포인터·구조체", "기본"
> 같은 서술뿐이고 **숫자를 지정한 적이 없다.** 아래 표는 그 서술에서 내가 유추한 값이며,
> 특히 `객체지향 = 2`는 "클래스·상속을 썼다"에서 한 단계 더 도약한 추정이다.
> **`FitScore`·갭 목록·ROI 순위가 전부 이 표에서 나온다** — 첫 실행 전에 사용자가 한 줄씩
> 확인하는 것이 P1의 첫 항목이다.

| 스킬 | 레벨 | 근거 | 지위 |
|---|---|---|---|
| Java, Spring Boot, Spring | 2 실습 | 클래스·상속·스프링부트까지 | [추정] |
| 객체지향 | 2 실습 | 클래스·상속을 직접 썼다는 서술에서 유추 | **[추정·도약]** |
| C | 1 기본 | 포인터·구조체 | [추정] |
| Python, React | 1 기본 | 본인이 '기본'이라고 명시 | [추정·근거 강함] |
| JavaScript | 1 기본 | **사용자가 언급하지 않았다.** 리액트를 쓰려면 필연이라는 유추 | **[추정·도약]** |
| **SQL, Linux, AWS** | **0** | **자격증만, 실물 경험 미확인** | [추정·보수적] |

자격증: 정보처리산업기사 · SQLD · 리눅스마스터 2급 · AWS AIF
학력 대졸(2~3년) / 경력 신입 / 요구 경력 상한 1년

**숙련도는 보수적으로 적는다.** 높게 적으면 갭이 숨고 도구가 "너는 준비됐다"고 거짓말한다.
낮게 적어서 생기는 손해는 이미 아는 걸 또 공부하는 정도이고, 높게 적어서 생기는 손해는
**못 뚫는 이유를 영원히 모르는 것**이다.

**자격증은 스킬 레벨을 채우지 않는다.** SQLD × SQL 실무 요구 = **부분 충족**이다.

> **미결정** — SQL·Linux·AWS를 실제로 써 봤다면 레벨을 올릴 것. 이 셋이 0인지 2인지가
> 갭 목록과 ROI 순위를 가장 크게 바꾼다.

### 5-2. 프로필은 주기적으로 갱신된다 — 결정됨

취준 중 스펙은 계속 바뀌므로 프로필은 고정값이 아니다. **노션이 입력창, repo가 정본이다.**

```
노션 'My Profile' DB  ──(주간 배치 ⑦)──▶  config/profile.yaml  ──▶  커밋
   ↑ 사람이 고치는 유일한 곳                    ↑ 코드가 읽는 정본
```

**단방향이다. `profile.yaml`을 손으로 고치지 않는다** — 다음 배치가 노션 값으로 덮어쓰기
때문이다. 양쪽에서 고칠 수 있게 두면 어느 쪽이 최신인지 판단하는 로직이 필요해지고, 그건
이 도구가 풀 문제가 아니다. (최초 1회만 `profile.yaml` → 노션으로 시딩한다.)

배치 ⑦이 하는 일:
1. 노션 `My Profile` 읽기
2. **스킬 이름이 `config/skills.py` 정본인지 검증.** 아니면 **반영하지 않고 경고**한다 —
   노션은 오타를 막아주지 않고, 오타는 조용히 '레벨 0'이 되어 **있는 스킬이 갭으로 나온다**
3. 통과한 값으로 `profile.yaml` 갱신 → 커밋(`profile: <변경 요약>`)
4. 변경이 있었으면 그 주 갭 추이 리포트에 `▲ 프로필 변경` 줄을 넣는다

두 가지 파생 요구사항이 따라온다.

**① 매칭 결과는 저장값이 아니라 파생값이다.** SQL 레벨을 0 → 2로 올리면 **과거 공고의
`FitScore`와 갭이 전부 바뀐다.** 그래서 `FitScore`·갭·ROI는 **매 주간 배치에서 누적
원천으로부터 다시 계산**한다. 노션 카드는 그 시점의 스냅샷일 뿐이고, 원천(repo)이 있으므로
언제든 재계산할 수 있다. 원천을 append-only로 쌓는 설계가 이걸 가능하게 한다.

**② 프로필 이력이 없으면 갭 추이를 해석할 수 없다.** §7의 리포트 예시 참조.
`profile.yaml`을 커밋으로 관리하므로 **git 이력이 그대로 프로필 변경 이력**이 된다 —
별도 이력 테이블이 필요 없다.

## 6. 파이프라인 — 일별 적재 + 주 1회 처리

**무거운 것과 놓치면 영구 손실되는 것만 매일 돌린다.** 나머지는 주 1회다.

```
매일 (GitHub Actions)  ── 수집·적재만. 노션·LLM 미사용
  ① 일자 멱등      오늘 이미 적재? → 종료            (repo 기준)
  ② 목록 수집      직군 키워드 × 워크넷 검색
  ③ 신규 판별      repo의 SourceKey와 대조           (repo 기준)
  ④ 상세 수집      신규 공고 1건 = 1요청. **요청 최다 단계**
  ⑤ 요건 추출      본문·우대사항 → {스킬, 필수/우대, 깊이}   사전 매칭, LLM 아님
  ⑥ repo 적재      append-only → **커밋 & 푸시**

주 1회 (GitHub Actions) ── 노션·LLM을 쓰는 것 전부
  ⑦ 프로필 동기화   노션 입력창 → profile.yaml 검증·갱신·커밋 (§5-2)
  ⑧ 통계 집계      그 주 적재분 + 누적 → 요건 분포
  ⑨ 기피 신호      정규식 + 근로자수 → Verdict        코드가 판단
  ⑩ 갭 매칭        요건 × 프로필 → FitScore + 갭      코드가 판단
  ⑪ ROI 계산       누적 통계 × 프로필 → "하나 채우면 몇 %"  ← 주간 배치가 맞다
  ⑫ 게이트         FitScore·Verdict로 노션 발행 대상 선별
  ⑬ LLM 설명       살아남은 것만
  ⑭ 노션 발행      공고 카드 + 리포트 3종(통계·ROI·갭 추이)
  ⑮ 슬랙           고적합만
```

### 6-1. 왜 이렇게 쪼개는가

1. **실패 격리.** 노션이나 Gemini가 죽어도 **수집은 계속 쌓인다.** 한 파이프라인이면
   뒷단 장애가 그날 수집을 통째로 날린다 — 그리고 공고는 마감되면 영구 손실이다.
2. **노션·LLM 부하가 1/7이 된다.** `SourceKey` 전량 조회 병목과 Gemini 하루 한도가 동시에
   해소된다(이 결정으로 §10-12가 닫혔다).
3. **급한 것과 급하지 않은 것이 갈린다.** 수집은 놓치면 복구가 안 되니 매일이어야 하고,
   통계·판정은 원천이 이미 안전하므로 급하지 않다.
4. **ROI는 애초에 주간 배치가 맞다.** "Docker를 채우면 34% → 52%"는 **누적 공고 전체를
   가상 프로필로 다시 평가**해야 나오는 값이라 일별 수집 중에 계산할 성질이 아니다.

### 6-2. 매일 쪽에서 반드시 지킬 것

| | 규칙 | 이유 |
|---|---|---|
| 멱등 | `CollectedDate`를 **repo**에 기록 | 노션은 주 1회만 열고, 3주 purge 대상이라 과거 날짜가 사라진다 |
| 신규 판별 | `SourceKey`도 **repo** | 매일 노션 전량 조회를 피한다 |
| 등록일 창 | **마지막 성공일 기준으로 확장** | 아래 |
| 상세 실패 | `요건 미확보`로 표시하고 **재시도 큐에 남긴다** | 아래 |

**⚠️ 실패한 날은 영구 손실된다.** upstream은 등록일 창을 실행 시점에서만 계산하고
(`오늘 - (REG_DAYS-1)`) 마지막 성공을 기억하지 않는다. 하루 실패하면 그날 등록된 공고는
다음 날 창에 안 들어온다 — 공고가 아직 열려 있어도 **등록일 필터에 걸려 못 본다.**
→ repo의 마지막 `collected_date`를 읽어 창의 시작을 거기까지 넓힌다. 기록이 repo에 있으므로
노션 purge와 무관하다(§10-13이 이 결정으로 닫혔다).

**⚠️ 상세 수집 실패를 조용히 넘기지 말 것.** ③ 신규 판별을 통과한 공고의 ④가 실패하면
요건이 없는 채로 남는다. `SourceKey`를 ⑥ 적재 시점에 쓰되 **`requirements_ok=false`로
표시**하고, 다음 날 그 목록을 먼저 재시도한다. 표시가 없으면 통계에 구멍이 남는데 아무도
모른다(§10-10이 이 결정으로 닫혔다).

## 7. 저장 — repo가 원천, 노션은 보는 곳

| | 담는 것 | 보관 | 갱신 |
|---|---|---|---|
| **repo (SQLite 또는 JSONL)** | 공고 원문 · 요건 레코드 · 일별 통계 · 멱등 기록 · `profile.yaml` | **영구** | 매일 커밋 |
| **노션** | 공고 카드 · 리포트 3종 · **프로필 입력창** | 공고는 3주 | 주 1회 |

**GitHub Actions 러너는 일회용이므로, 적재분을 워크플로가 직접 커밋해 되돌린다.**
upstream이 "노션이 유일한 정본"을 택한 이유가 바로 이 일회용 러너였다 — 커밋으로 그
제약이 해소된다. 하루 수십 행이면 몇 년을 써도 레포가 가볍고, **git 이력이 그대로 감사
기록과 백업**이 된다(§10-11이 이 결정으로 닫혔다).

워크플로 커밋 시 주의: `[skip ci]`를 커밋 메시지에 넣어 자기 자신을 다시 트리거하지 않게
하고, 푸시 충돌을 대비해 `pull --rebase` 후 푸시한다.

### 스키마 — 소급이 안 되는 결정

```sql
posting_snapshot          -- 매 수집마다 새 행. UPDATE 금지
  posting_id, collected_date, is_open, role,
  company, title, career_level, education, worker_count,
  requirements_ok,        -- ★상세/요건 확보 여부. false면 재시도 대상
  raw_text                -- ★원문 통째로

posting_requirement       -- 통계의 기본 단위
  posting_id, collected_date, role,
  skill_raw,              -- ★정규화 전 원문 토큰
  skill,                  -- 정본 (사전 적용 결과)
  requirement_type,       -- 필수 / 우대
  depth,                  -- 이해 / 경험 / 실무
  is_implied              -- ★함의로 파생된 것인가 (§10-14)

run_log                   -- 멱등 + 등록일 창 복구의 근거
  collected_date, status, listed, new, detail_ok, detail_failed
```

**`raw_text`와 `skill_raw`를 가공 전 원문으로 저장한다.** 스킬 사전은 계속 고쳐진다.
원문이 있으면 사전을 고칠 때마다 **과거에 소급 재적용**할 수 있고, 없으면 그 시점부터의
데이터만 남는다.

**공고는 UPDATE하지 말고 매 수집마다 append한다.** 그래야 공고가 언제 열리고 닫혔는지
복원되고 **생존기간**(며칠 만에 닫히는가 = 경쟁이 몰리는 조건)이 공짜로 나온다.

**`is_implied`를 반드시 남긴다.** `Spring Boot` → `Java` 파생을 그대로 집계하면 "Java를
명시한 공고 비율"과 "Java가 필요한 공고 비율"이 섞인다. 둘은 다른 지표다 — 전자는 시장이
무엇을 쓰는지, 후자는 내가 무엇을 준비해야 하는지를 말한다. **리포트는 둘 다 낸다**
(§10-14가 이 결정으로 닫혔다).

### 노션 속성

```
원본 15속성 + FitScore(number) · BlockingGap(multi_select) · PartialGap(multi_select)
             · WorkerCount(number) · SizeBand(select) · CollectedDate(date)
Kind: job | error | gap | stats        ← gap, stats 추가
```

⚠️ 속성을 추가하면 `notion_pub._schema_properties()`도 **같은 변경에서** 고쳐야 한다.
`test_notion.py::test_schema_has_every_property_publish_writes`가 "쓰는 속성은 전부
스키마에 존재한다"를 강제하므로 한쪽만 고치면 테스트가 깨진다. 그리고 **이미 만든 DB에는
속성이 소급 추가되지 않는다** — 노션에서 직접 추가하거나 DB를 새로 만들 것.

`Status`는 **사람 열**이다. 생성 시 `신규`만 넣고 기존 페이지를 절대 수정하지 않는다.
3주 보관 정리도 `Status=신규`인 페이지만 건드린다.

### 리포트 3종 (`Kind=stats` / `Kind=gap`)

> 📐 **아래 세 블록의 숫자는 전부 형식 예시이고 실측이 아니다.** 출력 모양을 정하기 위한
> 것이며, 실제 값은 첫 수집 이후에만 존재한다.

```
[시장 통계]  backend 직군 · 2026-W40 · 공고 112건 (예시)
  Java        명시 54% / 필요 71%   (필수 58%)   ← 명시·필요를 나란히 낸다
  Spring Boot 명시 54% / 필요 54%   (필수 41%)
  MySQL       명시 48% / 필요 48%   (필수 33%)
  Docker      명시 38% / 필요 38%   (필수 11%)   ← 간격이 크면 우대 비중이 높다
  Redis       명시 19% / 필요 19%   (필수  3%)

[내 갭 · ROI 순위]
  1. MySQL     채우면 지원가능 34% → 52%  (+18%p)
  2. Git 협업  채우면          52% → 63%  (+11%p)
  3. REST API  채우면          63% → 70%  (+7%p)
  ※ 묶음: MySQL + JPA 동시 → 34% → 61% (단독 합보다 크다)

[갭 추이]
  W40  MySQL, Git협업, REST API, JPA, Docker
  W41  MySQL, Git협업, JPA, Docker
  W42  Git협업, JPA, Docker
  ▲ W42: 프로필 변경 — MySQL 0→2        ← ★변경 시점을 반드시 표시한다
```

**갭 추이에 프로필 변경 시점을 표시하지 않으면 추이를 해석할 수 없다.** MySQL이 목록에서
사라진 것이 내가 배웠기 때문인지 시장이 덜 요구하게 됐기 때문인지 구분되지 않는다.
취준 도구에서 "내가 나아지고 있는가"가 핵심 지표인데 그 지표가 해석 불가능해진다.

**공고 페이지는 3주 뒤 보관 처리되지만 리포트 3종은 영구히 남긴다.**

### 슬랙

**고적합만 보낸다**(`FitScore >= 4` 이고 `Verdict != 위험`). 주 1회라 알림 피로는 낮다.
원본 규칙 유지 — 위험 공고 제목은 싣지 않고, 슬랙 실패가 노션 발행을 무효화하지 않는다.

## 8. 선결 과제 (P0)

### P0-1. 본인 Actions에서 work24에 닿는지 먼저 확인한다 (2분)

수집 주체를 **GitHub Actions로 확정**했으므로 이 과제는 살아 있다. upstream `ref.md` §19의
`ConnectTimeout` 원인은 미확정이고(가설 (a) WAF의 데이터센터 IP 차단, (b) 버스트 차단),
러너 IP가 해외 데이터센터라 (a)가 참이면 매일 실패한다.

**upstream의 CI 로그를 기다릴 필요는 없다.** fork 직후 `workflow_dispatch` 하나로 본인
계정에서 직접 확정할 수 있다 — `.github/workflows/probe-work24.yml` 참조.

| 결과 | 의미 | 다음 |
|---|---|---|
| `STATUS 200` + `totalRecordCount True` | 차단 없음 | Actions 계획 그대로 진행 |
| `FAIL ConnectTimeout` | 가설 (a) 확정 — 러너 IP 차단 | self-hosted runner(국내 IP) 또는 로컬 cron |
| 200인데 연속 호출에서 실패 | 가설 (b) — 버스트 | `WORKNET_REQUEST_GAP`만 올리면 된다 |

**이걸 통계층보다 먼저 돌린다.** 12주짜리 설계를 2분으로 검증하는 셈이고, 결과에 따라
수집 주체 결정이 바뀐다.

⚠️ 2026-09-30에 이 프로젝트를 분석한 클라우드 환경에서 403이 났지만 **그것은 위 가설의
증거가 아니다.** 그 프록시의 문서가 403을 자기 이그레스 허용 목록 거부로 규정하고, 상태
응답은 *policy denial or upstream failure*라 어느 쪽인지 알 수 없다 — 알 수 없으니 증거가
못 된다. 자기 환경의 정책 거부를 상대 서버의 차단으로 읽지 말 것.

### P0-2. 상세 페이지 라벨 확정 (`--probe-detail`)

라벨 문자열은 실제 공고 2건에서 관측했지만 **HTML 구조는 미검증**이다. 국내 IP에서 1회
돌려 `직무내용`이 추출되는지 확인. **실패하면 통계층과 개인층이 모두 성립하지 않는다.**

### P0-3. 목록 수집의 알려진 결함 3개 — 통계 편향으로 직결된다

원본에서는 "공고를 몇 건 놓치는" 문제였지만, **통계를 쌓으면 표본 편향이 된다.**

1. **뒤쪽 키워드가 조회되지 않는다.** `MAX_JOBS_PER_ROLE=30`에 걸리면 남은 키워드를
   건너뛴다. 실측 확인: `cloud` 5키워드 중 2개만 호출됐다. 뒤로 갈수록 정밀한 키워드라
   **정밀도 높은 쪽이 체계적으로 굶는다.** → 상한을 키워드 단위로 라운드로빈 분배.
2. **페이지네이션이 없다.** `currentPageNo=1`만 부른다. `PER_KEYWORD_FETCH=20`이 하드
   상한이고 초과분은 **경고 없이 사라진다.** `total_count()`를 이미 파싱하므로
   `total > len(rows)`일 때 경고 한 줄만 찍으면 드러난다.
3. **실패한 날 영구 손실** (§6-2).

**셋 다 고치기 전의 통계는 신뢰할 수 없다.** 순서상 P0-3이 통계층 구현보다 앞이다.

## 10. 미결정 사항

### 이번에 닫힌 것

| | 결정 |
|---|---|
| 수집 주체 | **GitHub Actions** (P0-1 스모크 테스트 결과에 따라 재검토) |
| 주기 | **일별 적재 + 주 1회 처리** (§6) |
| 원천 저장 | **repo, 워크플로가 커밋** (§7) — §10-11·12·13이 함께 닫혔다 |
| 프로필 갱신 | **노션 입력창 → repo 정본, 단방향** (§5-2) |
| 함의 요건 | **`is_implied`로 분리 저장, 리포트에 명시·필요 둘 다** — §10-14 닫힘 |
| 상세 실패 | **`requirements_ok=false` + 재시도 큐** — §10-10 닫힘 |

### 남은 것

1. **SQL·Linux·AWS 실제 레벨** ★ — 0인지 2인지가 갭·ROI를 가장 크게 바꾼다. P1 첫 항목.
   그리고 §5 표의 모든 레벨이 `[추정]`이므로 한 줄씩 확인이 필요하다.
2. **ROI 계산식** ★ — §2에서 최종 산출물이라고 선언했는데 정의가 없다. 정해야 할 것:
   분모(누적 공고 전체? 최근 N주?), 분자(필수 전부 충족? `FitScore >= 4`?),
   **묶음 탐색 범위**(조합은 지수적이므로 크기 2~3까지로 끊는 등의 경계).
3. **미매칭 토큰 리포트** — 사전에 없는 스킬은 통계에서 영구히 안 보인다(`Querydsl`·
   `Spring Batch`·`Elasticsearch`·`WebFlux`는 현재 사전에 없다). 주간 리포트에 미매칭
   상위 30개를 내야 사전이 자란다. ⚠️ 다만 **한국어 공고에서 "토큰" 경계를 정하는 것이
   쉽지 않다** — 공백 분할은 쓰레기가 나온다. 영문·숫자 연속과 카타카나 정도로 좁히거나
   n-gram이 필요하다. 처방을 과소평가하지 말 것.
4. **직군 키워드 확정** — §4는 초안. 실측 건수를 보고 조정.
5. **노션 DB** — upstream 것과 **반드시 별도**. `--init-db`로 새로 만든다.
6. **기피 조건 hard/soft 등급** — §3-1은 초안. hard로 올릴 때마다 잔존 건수 실측.
